* Introduction

This document describes the compiler architecture of =smd::forth=, a compile-time and runtime-capable Forth compiler in C++26.
Like its sibling document for the Scheme proof of concept (=~/src/compile-time-scheme/main/docs/compiler_architecture.org=), it exists to translate compiler jargon into terms familiar to working C++ developers.
Every code sample below is transcluded from the real source tree by a UUID anchor, never hand-copied prose that might drift from what actually compiles.
This document is filled in incrementally, one pipeline phase at a time, as each phase's implementation step lands (=docs/forth-plan.md=).
As of this revision the lexical layer (step F5), the parser combinators and grammar (steps F4 and F7), the syntax tree (step F6), and the elaborated core and resolution pass (step F11) all exist; later sections describe phases that are planned but not yet implemented, and carry no transclusion until their step lands.

* Pipeline overview

The compiler is a single staged pipeline, run entirely in =constexpr= evaluation, that can then be re-run at ordinary runtime against fresh input.
Each stage consumes the previous stage's output and produces a new, more refined representation; no stage mutates another stage's data in place.

The three codegen targets on the right are three different ways of running the same elaborated core: an immediate tree-walking evaluator, a compiled instruction array executed by a small stack machine, and a Beman Execution sender graph for structured-concurrency integration.
All three read the same elaborated core; none of them re-parses source text or re-derives stack effects.

* Phase 1: Source Text and the Lexical Layer

DRAFT — pending author revision.

Forth source is plain text: whitespace-delimited words, numeric literals, and =( ... )= stack-effect comments.
Unlike the Scheme front end, there is no reader/eval loop and no =IMMEDIATE=; the entire program is parsed structurally, once, before anything executes (=docs/forth-plan.md= D5).
The lexical layer (step F5) folds every word to uppercase at scan time, so nothing downstream of it ever needs to re-fold case.
A word, in this project's sense, is any run of characters that is not ASCII whitespace; numbers are recognized textually, not by any special punctuation, so =-1= is a number but =1-= and a bare =-= are words.

Forth's own notion of intertoken space is wider than plain whitespace: it also swallows =\ ...= line comments and =( ... )= parenthesized comments, repeating until none of the three remain.
A colon definition's declared stack-effect comment is the one =( ... )= exception to "comments are just whitespace": step F7's grammar captures its span (rather than discarding it, the way ordinary comment-skipping does) whenever that comment contains =--=, so a later step (F12) can re-slice the original source text through the span without the tree ever duplicating the comment's characters.

* Phase 2: Applicative Parser Combinators and the Forth Grammar

DRAFT — pending author revision.

Recursive descent, hand-rolled as a tree of =if=/=else=/=while=, is error-prone and hard to compose.
Instead the front end is built from parser combinators: small composable objects that snap together into a grammar the way Lego bricks snap together into a model.
Because C++26 =constexpr= evaluation cannot easily juggle capturing lambdas converted to function pointers, parsers are represented as ordinary callable objects (functors with =operator()=), registered against the project's =functor=/=applicative=/=alternative= typeclasses (imported in step F3, exercised for real the first time in step F4).

#+transclude: [[file:../src/smd/forth/parser/parser.hpp::5f36b161-a5b2-45a9-82e4-4d4679a8a60e]] :lines 2- :src cpp :end "5f36b161-a5b2-45a9-82e4-4d4679a8a60e end"

Alternatives compose with an ordered-choice operator: try the first parser, and only fall back to the second if the first failed without having consumed any input, so a parser that has committed to a partial match is never silently backtracked out of.

#+transclude: [[file:../src/smd/forth/parser/parser.hpp::2a77ed5e-0863-4a2a-8ea0-1b03b56ffeb4]] :lines 2- :src cpp :end "2a77ed5e-0863-4a2a-8ea0-1b03b56ffeb4 end"

Step F7's grammar (=src/smd/forth/reader/read_program.hpp=) is the production parser built from this combinator library, per the project's decision D6 that the combinator library is the parser, not merely a tool for scanning atoms.
Every token-level production — names, numbers, keywords, the stack-effect comment capture — is composed directly from the F4/F5 free functions above and from Phase 1's lexical layer.
The grammar's *nested* productions are the one place this project accepts a documented exception rather than a silent hand-rolled fallback: an =IF= that can itself contain another =IF= has no finite combinator type to compose it from (the combinator's own C++ type would have to mention itself), and building syntax-tree nodes needs a mutable arena threaded alongside the cursor, which the combinator calling convention (=cursor -> parse_result<T>=) has no slot for.
DIV-0005 records this in full; the entry point below still returns a =foundation::result=, exactly like every combinator above it, and every recursive production is bounded by an explicit =MaxDepth= template parameter rather than being allowed to recurse without limit.

* Phase 3: The Syntax Tree

The syntax tree is the parser's output: a direct, structural record of what the source text says, before anything has been resolved against the dictionary or checked for stack-effect soundness.
Every tree in this compiler — the syntax tree, the elaborated core, and the compiled instruction program — is a flat arena of trivially destructible nodes addressed by integer =arena_box= handles (=docs/forth-plan.md= D3); there is no heap-backed =fix=/=Box= recursion anywhere in the compiled pipeline.
The syntax tree's closed node type, =syn_node=, is a =std::variant= over every syntax form Forth needs: literals, bare words, colon definitions, the three control-flow shapes (=IF=, =BEGIN ... UNTIL=, =BEGIN ... WHILE ... REPEAT=, =DO ... LOOP=), and the four declaration forms (=VARIABLE=, =CONSTANT=, =CREATE=, =' NAME= tick).
=syn_node= is forward-declared before it is defined, which is what lets its own composite alternatives (a colon definition's body, an =IF='s two branches, and so on) hold handles to sibling nodes of the very type being defined — an =arena_box<T, MaxNodes>= handle only ever stores an integer, so it never needs =T= to be complete, and the recursion closes without reaching for =fix= at all.

#+transclude: [[file:../src/smd/forth/reader/syntax_tree.hpp::e74ee0de-460c-41da-aeb4-23235b52df77]] :lines 2- :src cpp :end "e74ee0de-460c-41da-aeb4-23235b52df77 end"

The three control-flow node kinds each carry one or two bodies — sequences of child-node handles — and the colon-definition node additionally carries the raw span of a stack-effect comment for step F12 to re-slice out of the original source text later, rather than duplicating that text into the tree now.

#+transclude: [[file:../src/smd/forth/reader/syntax_tree.hpp::e701a3a8-aeff-4b78-9dd5-df3b16fcb6b8]] :lines 2- :src cpp :end "e701a3a8-aeff-4b78-9dd5-df3b16fcb6b8 end"

The closed node type itself ties every kind above into a single variant that a =foundation::tree_arena= can store flat, with every capacity (arena size, body length, name length) left as a template parameter rather than a hardcoded constant.

* Phase 4: Elaboration (Resolution and Stack-Effect Checking)

DRAFT — pending author revision.

Elaboration is compiler jargon for "figuring out what the code actually means."
Where the syntax tree only records what the text says structurally, the elaborated core additionally resolves every word reference against the dictionary and checks that every definition's stack effect is sound before anything is allowed to run (step F12).
Step F11 (this section) owns resolution: it walks the syntax tree in program order, threading a =machine::dictionary= forward exactly as a traditional Forth cross-compiler would, and produces a second flat arena — the elaborated core — in the same trivially destructible, =arena_box=-addressed style as the syntax tree (D3).
Every syntax-tree word reference (a bare word or a =' NAME= tick) becomes one of a small number of already-resolved node kinds: a direct primitive invocation, a call to another definition by its dictionary index, a variable's address, a constant's value, or an execution token — there is no dictionary lookup left to do once elaboration finishes.

#+transclude: [[file:../src/smd/forth/elaborator/elaborated_core.hpp::8a9a3c73-7150-4019-97f5-0485af9c56bb]] :lines 2- :src cpp :end "8a9a3c73-7150-4019-97f5-0485af9c56bb end"

The three control-flow node kinds mirror the syntax tree's =IF=/=BEGIN...UNTIL=/=BEGIN...WHILE...REPEAT=/=DO...LOOP= shapes one for one, and =core_seq= is the one new shape: it is what a colon definition's elaborated body becomes, and it is the node a =colon_word= dictionary entry's =core_id= actually points at.

#+transclude: [[file:../src/smd/forth/elaborator/elaborated_core.hpp::36591b76-b56e-4425-a5c6-a6f32dda00ae]] :lines 2- :src cpp :end "36591b76-b56e-4425-a5c6-a6f32dda00ae end"

The closed node type ties every kind into one variant, exactly like the syntax tree's own =syn_node=, and for the same reason: an =arena_box= handle only ever stores an integer, so the composite kinds above can hold handles to sibling nodes of the very type being defined without ever reaching for =fix=.

#+transclude: [[file:../src/smd/forth/elaborator/elaborated_core.hpp::6100f8d6-3f92-47ce-b4e2-d4137a801740]] :lines 2- :src cpp :end "6100f8d6-3f92-47ce-b4e2-d4137a801740 end"

Elaboration threads a dictionary forward and mutates it as it goes: a colon definition's body is resolved against whatever the dictionary looks like *at that definition's own position in the source*, never against the whole program at once.
This is what makes redefinition behave the way a traditional (cross-compiling) Forth expects: defining a word a second time does not retroactively change any earlier definition that already called the old one.
=machine::dictionary= never overwrites or removes a shadowed entry — it only ever appends — so an earlier colon definition's already-elaborated =core_call= keeps pointing at the old entry's index by construction, while later code that looks the name up again reaches the new one first (newest-first lookup).
Elaboration does not treat redefinition as an error; it records it as a warning in the =compiled_unit='s own collected-diagnostics channel and keeps going, matching the traditional Forth expectation that redefining a word is routine, not exceptional.

Step F12 (this section) owns stack-effect checking: it runs as part of =elaborate= itself, per D9, so a program that fails analysis fails elaboration — there is no separate "type-check" pass a caller can skip.
The checker is an abstract interpretation over the elaborated core, computed once per colon definition, that tracks two independent quantities: a data-stack effect and a return-stack depth delta.
The data-stack side uses a small lattice: a =known= value is a concrete =(inputs, outputs)= pair, where =inputs= doubles as the definition's minimum entry depth and =outputs= is the depth left behind measured from that same entry point; the lattice's top value, =unknown=, suppresses further depth-based checking downstream rather than erroring, and is produced only by input-dependent primitives (=?DUP= today; whatever primitive =EXECUTE= becomes once step F18a adds it).
The return-stack side is tracked as a plain running integer, not a lattice, because none of =>R=/=R>=/=R@= are ever input-dependent — only the data-stack side can go =unknown=.

#+transclude: [[file:../src/smd/forth/elaborator/stack_effect.hpp::3fd1b4b2-6cf1-4b6e-9b6b-3f2c0a8f7d21]] :lines 2- :src cpp :end "3fd1b4b2-6cf1-4b6e-9b6b-3f2c0a8f7d21 end"

Composing two effects in sequence follows the standard "stack level" derivation: the combined entry requirement is whatever the first effect needs, plus however much more the second effect needs once the first has already produced its share; combining two verified-compatible =IF=/=ELSE= arms into the =IF= node's own contributed effect works the same way, using whichever arm demands more at entry.
A subtlety worth calling out explicitly: =IF=/=ELSE= arms are compared by their *net* effect (the depth delta, =outputs - inputs=) rather than by the full pair, because two arms can have different shapes and still be safe to run interchangeably — =NEGATE= (1,1) and an implicit empty =ELSE= (0,0) both have net effect zero despite different shapes, and the canonical Forth-2012 idiom =: ABS DUP 0< IF NEGATE THEN ;= depends on exactly this reading to type-check at all.
The main walk (=analyze_body=) recurses into every control structure's nested bodies, diagnosing four of the plan's five error shapes as it goes: unequal =IF=/=ELSE= net effect, a loop body (=DO=, =BEGIN...UNTIL=, or =BEGIN...WHILE...REPEAT=) with the wrong net effect, and a return-stack depth that fails to return to zero across any single control-structure body.
=RECURSE= poses a real fixed-point problem — the callee's effect is exactly the thing being computed — and this step does not attempt to solve it: a definition's declared =( ... )= effect comment, when present, is trusted as the assumed effect of its own =RECURSE= call sites; when absent, a self-call is simply treated as =unknown=, exactly like =?DUP=.
=EXIT= is handled conservatively rather than with full flow sensitivity: once encountered while folding a body's items, remaining items in that same body are unreachable and are not visited at all, which is sound for an unconditional trailing =EXIT= but does not attempt to reconcile an early-return depth against the definition's eventual fall-through depth when =EXIT= sits inside a conditional (see DIV-0006).

#+transclude: [[file:../src/smd/forth/elaborator/stack_effect.hpp::7c2a9e5d-3b8f-4a1e-9d6c-8e4f1b2a6c9d]] :lines 2- :src cpp :end "7c2a9e5d-3b8f-4a1e-9d6c-8e4f1b2a6c9d end"

The fifth diagnosis — an =EXIT= lexically nested inside a =DO= loop's body without an =UNLOOP= to appease first — is a separate, purely lexical scan, independent of the depth-tracking walk above; it exists because =UNLOOP= is not a primitive yet (step F17 adds real counted-loop machinery), so there is currently no way to leave a =DO= loop's parameters consistent before an early exit, and the shape is diagnosed unconditionally rather than trying to verify an =UNLOOP= that cannot exist.
=analyze_colon_effect= is the entry point =elaborate_colon_def= calls, between building a definition's =core_seq= and installing its =colon_word=: it runs the lexical =EXIT=-in-=DO= scan, then the depth-tracking walk, then checks that the whole definition ends return-stack balanced, then — if a =( ... )= comment was written — compares the declared effect against the computed one, verbatim, field for field.
Reading a declared effect's *text* back out of its captured span is new work this step needed that step F11 did not: =elaborate='s signature grew a =std::string_view source= parameter (the exact program text a =syntax_tree= was parsed from), threaded down to wherever a colon definition's =declared_effect= span needs re-slicing.

* Phase 5: Codegen and the Three Backends

DRAFT — pending author revision.

Codegen turns the elaborated core into a compiled instruction program: another flat, trivially destructible =tree_arena=, this time of machine instructions rather than syntax forms.
That same instruction program is then interpretable three ways: directly by a tree-walking evaluator, by a small classic stack machine (two fixed-capacity stacks, an arena data space, and an output buffer), and by a Beman Execution sender graph in which Forth's one-shot, dynamic-extent control words (=EXIT=, =LEAVE=, =CATCH=/=THROW=) map directly onto the sender/receiver completion discipline.
Step F13 (this section) is the first of the three to land, and it skips codegen entirely: it is a *reference* interpreter, walking the elaborated core directly by structural recursion rather than flattening it into an instruction array first.
This is deliberate, not a shortcut taken for its own sake — step F14's stack-machine codegen and VM is checked against this evaluator's own output (the plan's own merge criterion for F14 runs the same F13 test programs through both backends and requires they agree), so F13 has to exist as a trustworthy, independently-derived oracle before F14's flattening/back-patching machinery has anything to be checked against.
=eval_direct.hpp= lives under =src/smd/forth/machine/=, not =src/smd/forth/elaborator/=, per the plan's own placement — it depends on =elaborator::compiled_unit= the same way every =elaborator/*.hpp= header already depends on =machine/*.hpp= for =dictionary=/=forth_state=, and both directories fold into the same single build target (=compile-time-forth.forth=), so this is a documented, one-directional layering choice, not a new library boundary or a circular dependency.

#+transclude: [[file:../src/smd/forth/machine/eval_direct.hpp::0faeac96-c46d-48bb-a1db-c21191d35022]] :lines 2- :src cpp :end "0faeac96-c46d-48bb-a1db-c21191d35022 end"

Primitives run through =machine::apply_primitive= — F8's imperative implementation, the one that actually mutates a =forth_state= — never through F12's =elaborator::primitive_data_effect= table, which exists purely for abstract interpretation and has no notion of actually running anything.
A =core_call= recurses structurally into the callee's own core, found the same way F12's =analyze_body= already finds a call target's effect: =unit.dictionary.entry_at(word_index)= to get the =colon_word=, then =unit.arena.get(colon_word.core_id)= to reach its =core_seq=.
=core_if=, =core_begin_until=, and =core_begin_while= become real control flow this time, conditionally or repeatedly evaluating their bodies against the live machine state rather than only predicting a depth the way F12's analysis did — =core_begin_until='s body runs at least once and re-runs until the flag it leaves behind is true; =core_begin_while='s condition runs before every iteration (including the first) and the loop stops the moment it leaves a false flag.
=core_exit= is the one genuinely new piece of control-flow plumbing: it is a runtime early return, threaded through the evaluator's own =foundation::result<eval_signal>= channel rather than a C++ exception, matching this project's one-shot, dynamic-extent nonlocal-control invariant (D11).
An =eval_signal::exited= return value propagates upward through every nested control-structure body it passes through — unevaluated code after it in the same body list is simply never visited — all the way up to the nearest enclosing =core_call=, which is where it is absorbed: a call is its own fresh definition boundary, so a callee's own =EXIT= never unwinds past the call that invoked it.
=DO...LOOP= has no loop-index machinery at the core level yet (no node pops a loop's =(limit start)= pair or exposes =I=/=J=) — that is step F17's own deliverable — so =core_do_loop= is diagnosed rather than evaluated at all; none of F13's own merge criteria exercise it.

Every misuse the evaluator can observe is a diagnosed =foundation::result= error exactly as it would be calling =apply_primitive= or a =cell_stack= directly by hand: stack underflow/overflow, division by zero, output-buffer overflow, and one new failure mode this step introduces — budget exhaustion.
A nonterminating program (=BEGIN FALSE UNTIL= never becomes true) would otherwise hang a =constexpr= evaluation forever, since the compiler is perfectly willing to keep folding a =constexpr= function that never returns; the evaluator instead threads a plain decrementing =int= "fuel" counter through every node it visits and diagnoses exhaustion rather than looping.

#+transclude: [[file:../src/smd/forth/machine/eval_direct.hpp::4caeb07c-70eb-4256-9a53-f48d9fd89fe1]] :lines 2- :src cpp :end "4caeb07c-70eb-4256-9a53-f48d9fd89fe1 end"

This step is also the first to need `.`, `.S`, `EMIT`, and `CR` as real, runnable primitives (D10) — F8 never wired them, and one further word this step's own merge criteria need verbatim, `1-`, was missing from the language entirely (DIV-0007 records both gaps and this step's fix).
=eval_program= is the pipeline's first true end-to-end milestone: read (F5/F7) into a syntax tree, elaborate (F11/F12) into a =compiled_unit= whose every definition has already passed stack-effect analysis, then evaluate that =compiled_unit= directly, all in one =constexpr= chain a =static_assert= can exercise at compile time.

** The classic stack machine (step F14)

Step F14 (this section) is the second of the three backends, and the first to actually do codegen: it flattens the same elaborated core F13 walks directly into a linear array of machine instructions, then executes that array with an explicit instruction-pointer loop, rather than recursing through the core's own tree shape at every step.
An instruction is one opcode plus a single immediate =cell= operand — about as close to a real machine's own encoding as a =constexpr=-friendly C++ type can get.

#+transclude: [[file:../src/smd/forth/machine/instruction.hpp::5b9e9c1a-6b0e-4b7a-9f3a-7a5b7c9d2e1f]] :lines 2- :src cpp :end "5b9e9c1a-6b0e-4b7a-9f3a-7a5b7c9d2e1f end"

Only eight of the seventeen opcodes have real codegen and VM behavior as of this step: =push=, =push_xt=, =prim=, =call=, =ret=, =branch=, =branch0=, =halt=.
The remaining nine reserve opcode space for later steps without committing to a guessed-at design before those steps do the real work: =do_setup=, =loop_step=, =plus_loop_step=, =push_index=, =leave=, and =unloop= are all =DO ... LOOP= machinery (step F17's own deliverable), and =execute=, =catch_mark=, and =throw_op= are step F18a's (execution tokens and exceptions).
=codegen= diagnoses a =core_do_loop= node as "not implemented until F17" rather than emitting any counted-loop opcode, mirroring F13's own identical choice for =eval_direct.hpp=; the VM diagnoses any of the nine reserved opcodes if it is ever asked to execute one, rather than treating an unimplemented opcode as undefined behavior (D7) — unreachable in practice, since this step's own codegen never emits them.
DIV-0008 records this scope cut, along with a second one: =compiled_program='s own =required_stack_depth=/=required_return_depth= fields exist (the plan calls for "required stack capacities" alongside the word table and data-space size) but default to =-1=, "not computed" — F12's stack-effect analysis computes each definition's net effect and minimum entry depth, not a whole-program running peak, and no other analysis in the pipeline yet computes one either.

#+transclude: [[file:../src/smd/forth/machine/instruction.hpp::c520a0cc-7a47-4db4-a218-617a1cfebe8d]] :lines 2- :src cpp :end "c520a0cc-7a47-4db4-a218-617a1cfebe8d end"

=compiled_program= is the artifact that survives from a =constexpr= codegen call to an ordinary-runtime VM call unchanged: a literal type, trivially copyable, bundling the flat instruction array with a word table (=entry_points=, one instruction index per dictionary entry, =-1= for anything that is not a colon word — primitives, variables, and constants are inlined at each reference site instead of called), the top-level program's own starting instruction index, and the data-space size the source =compiled_unit= had already allotted.

=codegen= walks =unit.dictionary= in index order, emitting each colon word's own body before moving to the next entry, and records that word's entry point *before* emitting its body rather than after.
This ordering is what lets every =call= instruction's operand resolve to a real instruction index without any back-patching: F11's static-binding discipline guarantees a =core_call='s target is always either an earlier word (already emitted, by construction, since dictionary order is walked forward) or the very word currently being emitted (=RECURSE=, a self-call — already in the word table by the time its own body's self-reference is reached, because the entry was recorded first).
Back-patching is reserved for what actually needs it: a control structure's own *forward* branch, whose target instruction has not been emitted yet at the point the branch itself is.

The VM's own =run= loop is the pay-off of compiling =EXIT= to a literal =ret= instruction rather than threading an =eval_signal= through nested C++ call frames the way F13's evaluator has to: the return stack (=forth_state::returns()=, already shared between calls and, later, loop parameters, per ordinary Forth convention) already holds exactly the call chain a =ret= needs to unwind, so "pop a return address, jump to it" is the whole of =EXIT='s runtime behavior — no propagation logic of its own is needed anywhere else in the loop.
A plain decrementing =int= "fuel" counter, consumed once per instruction fetched, bounds execution exactly the way F13's own per-core-node fuel bounds a nonterminating =BEGIN ... UNTIL=; budget exhaustion is a diagnosed error at the VM level too, not a hang.

F14's own merge criterion is the "survives-to-runtime proof": every one of F13's own merge-criterion programs (=SQUARED=, =ABS=, =COUNTDOWN=, and =SPIN='s budget exhaustion) is compiled once into a =constexpr compiled_program= declared at namespace scope, then run through the VM twice against that *same* object — once inside a =static_assert= (compile time) and once inside a Catch2 =TEST_CASE= (ordinary runtime) — proving the identical compiled artifact works both ways, not merely that the same source text re-compiles identically twice (=vm.test.cpp=).

* Phase 6: The Public One-Shot API (step F15)

Every phase above this one is reachable only by naming =reader::read_program=, =elaborator::elaborate=, and =machine::codegen=/=machine::run= individually, in order, by hand — exactly the small local =compile()= helper every one of F13's and F14's own test files already builds for itself.
Step F15 (this section) promotes that same four-call sequence to the one thing an external caller is meant to use: =compiled_forth<Source>=, a namespace-scope =constexpr= value keyed on the Forth source text itself, plus a small =forth_program= convenience surface to run it and inspect the result.

=source_literal<N>= is what makes a whole Forth program's text usable as a template argument: a null-terminated =char= array copy of the literal, deduced via CTAD from a =char const (&)[N]= constructor argument, with a =.view()= accessor that drops the trailing null.
The pattern is reused, not copied, from =~/src/compile-time-scheme/main='s own =source_literal<N>=/=compiled_closure<Source>= (docs/forth-plan.md section 5) — reimplemented here under =smd::forth= with this project's own conventions, composing three pipeline stages rather than Scheme's single =compile_to_closure= call.

=forth_program= bundles an already-compiled =machine::compiled_program= with the runtime capacities (=StackDepth=, =RStackDepth=, =MaxData=, =MaxOut=) a fresh =machine::forth_state= needs, and adds the three accessors the plan names: =run= returns the full =result<forth_state>= (success or the first diagnosed runtime error, e.g. budget exhaustion); =stack= and =output= are best-effort convenience snapshots — a =foundation::static_vector= built from a fresh run's own resulting state regardless of whether that run completed successfully, since =machine::run= mutates its =forth_state= argument in place even on an early error return.
=stack='s cell order is bottom-to-top, matching =machine::primitive::dot_s='s own printed order.
Because a namespace-scope =constexpr= value cannot carry mutable state of its own, each of =run=/=stack=/=output= reconstructs a fresh =forth_state= and re-executes the whole program from scratch — correct and cheap for programs this size, but something a caller running a large program in a hot loop should not do by accident.

=compiled_forth<Source, ...>= is the public entry point itself: it runs the whole read → elaborate → codegen pipeline exactly once, at namespace-scope =constexpr= initialization, and stores the result as a ready-to-run =forth_program=.
Every pipeline-stage capacity is its own template parameter with the same default its owning stage already uses (D2 — no divergence, since parameterizing rather than hardcoding is the D2-compliant choice); =StackDepth=/=RStackDepth=/=MaxOut= are new capacities this step introduces for the runtime state, chosen generously for a one-shot caller.
A =Source= that fails to parse, fails elaboration, or overflows any capacity is a hard compile error: =.value()= on a failed =foundation::result= inside a =constexpr= initializer is not a core constant expression, so the whole translation unit fails to compile — the same discipline F13's and F14's own namespace-scope =constexpr= test programs already relied on for known-good inputs, now the *public* contract (=src/smd/forth/test_neg_syntax_error.cpp= exercises the failure side deliberately, as a dedicated CTest negative-compile test — new infrastructure this step introduces, ahead of its originally-planned home at step F21).
