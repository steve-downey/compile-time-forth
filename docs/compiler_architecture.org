* Introduction

This document describes the compiler architecture of =smd::forth=, a compile-time and runtime-capable Forth compiler in C++26.
Like its sibling document for the Scheme proof of concept (=~/src/compile-time-scheme/main/docs/compiler_architecture.org=), it exists to translate compiler jargon into terms familiar to working C++ developers.
Every code sample below is transcluded from the real source tree by a UUID anchor, never hand-copied prose that might drift from what actually compiles.
This document is filled in incrementally, one pipeline phase at a time, as each phase's implementation step lands.

This document went through one architectural pivot.
Steps F5 through F15 (=docs/forth-plan.md=, the superseded R1 plan) built a classic ahead-of-time pipeline: a structural parse into a syntax tree, a separate elaboration pass that resolved names and checked stack effects, and codegen into a choice of backend.
DIV-0011 (=docs/divergences/DIV-0011-true-forth-pivot.md=) retired that design in favor of D13: the Forth-2012 section 3.4 text interpreter, with no reader phase and no elaboration phase, is the architecture.
Steps F24/F25 built the new front end alongside the old one; step F26 ("the cut", =docs/forth-plan-2.md=) deleted the R1 pipeline outright once the new one could stand on its own.
Phases 2 through 5 below described the deleted pipeline (grammar, syntax tree, elaboration, and two of its three codegen backends) and have moved to =docs/history/architecture-grammar-era.org=, a frozen one-time snapshot — they are no longer part of this living document's own read path.
As of this revision the lexical layer (Phase 1), the public one-shot API (Phase 6), the text interpreter (Phase 7), the colon compiler and session image (Phase 8), the cut itself (Phase 9), immediacy and control flow (Phase 10), execution tokens and defining words (Phase 11), and parsing words and strings (Phase 12) are current.

* Pipeline overview

The compiler is a single staged pipeline, run entirely in =constexpr= evaluation, that can then be re-run at ordinary runtime against fresh input — but as of D13 (step F24 onward) it is not a classic ahead-of-time pipeline with distinct parse/elaborate/codegen stages.
Source text is scanned and consumed by one loop, the Forth-2012 outer text interpreter, which resolves each word against the dictionary the moment it meets it and either runs it (interpreting) or emits code for it (compiling, inside a =:= ... =;= definition) in the same pass.
There is no syntax tree and no separate elaboration phase; "compiling" a program and "running its top level" are the same act.

#+begin_src mermaid
flowchart LR

    B --> C[Code space]
    B --> D[Dictionary]
    B --> E[Data space]
    C --> F["Stack-machine VM (re-run, e.g. from a session image)"]
    C --> G["Sender/receiver CPS backend (planned, step F33)"]

Code space, dictionary, and data space together are D15's "session image" (=interpreter::session=, Phase 8): a trivially copyable literal that survives from the one =constexpr= evaluation that built it into ordinary runtime code, where the VM can run one of its own defined words again.
The stack-machine VM and its instruction set (Phase 9) are retained unchanged from the R1 pipeline (D16); only what feeds them changed.
The sender/receiver backend is still planned, not yet built (step F33).

* Phase 1: Source Text and the Lexical Layer

Forth source is plain text: whitespace-delimited words, numeric literals, and =( ... )= stack-effect comments.
The lexical layer (step F5) folds every word to uppercase at scan time, so nothing downstream of it ever needs to re-fold case.
A word, in this project's sense, is any run of characters that is not ASCII whitespace; numbers are recognized textually, not by any special punctuation, so =-1= is a number but =1-= and a bare =-= are words.
Unlike the R1 pipeline this lexical layer originally fed (=docs/history/architecture-grammar-era.org=), there is no structural parse of the *whole* program before anything executes: D13 (step F24 onward) makes this scanner the token layer underneath the Forth-2012 outer text interpreter (Phase 7), which scans, resolves, and acts on one word at a time as it goes.

Through step F28, Forth's own notion of intertoken space was wider than plain whitespace: this scanner also swallowed =\ ...= line comments and =( ... )= parenthesized comments, repeating until none of the three remained (=skip_forth_space=, since deleted).
Step F29 re-expresses =\= and =(= as ordinary immediate dictionary words instead (D19; see Phase 12): a source =(= or =\= character is now an ordinary one-character word, like any other name that happens to be followed by whitespace, and comments are no longer a scanner-level concept at all — =skip_intertoken_space=, plain ASCII whitespace only, is the only thing this layer itself still does between one token and the next.
A colon definition's declared stack-effect comment is unaffected by that reexpression: the interpreter's own =scan_colon_header= (Phase 8) still captures a =( ... )= comment's span directly (rather than letting the ordinary =(= word consume it) whenever that comment immediately follows a =:= definition's own name and contains =--=, so the declared effect can be re-sliced out of the original source text later without ever duplicating the comment's characters into a tree (D20: captured, not yet verified — that lands at step F30).
See Phase 12 for =\=/=(='s own reexpressed code and =scan_delimited=, the shared scanning primitive every F29 parsing word (including them) is built from.

**D19's token-layer location, resolved at step F26.**
D19 (=docs/forth-plan-2.md=) puts the combinator library "below the word," owning scanning and classification over the machine's own input source, and gave the step that first needed this layer from outside =reader/= (F24, the text interpreter) the choice of where =forth_chars.hpp= itself should live: under =interpreter/=, or down in =parser/= where the rest of the combinator library already sits.
F24 deferred that choice (DIV-0012): =reader/= was still alive for the R1 pipeline, and moving this one header a step early would have meant touching every one of that pipeline's own consumers for no F24 benefit.
Step F26 ("the cut") closes it: =reader/= is deleted wholesale, so the deferral's own reason is gone, and this file now lives at =src/smd/forth/parser/forth_chars.hpp=, in namespace =smd::forth::parser= — D19's own original recommendation, not =interpreter/=, since the combinator library is machinery several consumers (the interpreter now, F29's parsing words later) sit on top of, not something the interpreter itself owns. DIV-0012's own record is updated in place with this closure; see it for the fuller history.

* Phase 6: The Public One-Shot API (step F15; retargeted at step F26)

Step F15 built =compiled_forth<Source>=, a namespace-scope =constexpr= value keyed on the Forth source text itself, over the R1 pipeline: read, elaborate, codegen, each named by hand once, inside the variable template's own initializer.
Step F26 ("the cut") retargets it onto D15's session image (=interpreter::build_session=, Phase 8) once that pipeline is deleted — see DIV-0014 for the full record of what changed and why; this section describes the retargeted shape.

=source_literal<N>= is unchanged by the retarget: it is what makes a whole Forth program's text usable as a template argument, a null-terminated =char= array copy of the literal deduced via CTAD from a =char const (&)[N]= constructor argument, with a =.view()= accessor that drops the trailing null.
The pattern is reused, not copied, from =~/src/compile-time-scheme/main='s own =source_literal<N>=/=compiled_closure<Source>= (docs/forth-plan.md section 5).

#+transclude: [[file:../src/smd/forth/forth.hpp::18245977-b4d2-4011-bac7-a36f7680aeb4]] :lines 2- :src cpp :end "18245977-b4d2-4011-bac7-a36f7680aeb4 end"

Under D13/D14 there is no separate "compile" phase distinct from "run the top level": the text interpreter both compiles =:= ... =;= definitions and directly executes every top-level word as it meets it, in the same pass.
R1's =forth_program= therefore compiled once and *ran* the result fresh, from scratch, once per accessor call; the retargeted =forth_program= wraps an already-built =interpreter::session= instead, and none of its three accessors re-executes anything — the whole program already ran once, when =compiled_forth= built the session.
=run= now returns the built session image itself (never fails at the call site: any failure already happened, at compile time); =stack= and =output= are thin accessors over that same session's own =stack=/=output= fields.
=stack='s cell order is bottom-to-top, matching =machine::primitive::dot_s='s own printed order — a convention the session's own =stack= field (F26's own addition to =interpreter::session=, Phase 8) preserves from the R1-era accessor of the same name.

#+transclude: [[file:../src/smd/forth/forth.hpp::bb43d007-745e-4e1b-8057-b97766788d6b]] :lines 2- :src cpp :end "bb43d007-745e-4e1b-8057-b97766788d6b end"

=compiled_forth<Source, ...>= is the public entry point itself: it builds =Source='s whole session (=interpreter::build_session=) exactly once, at namespace-scope =constexpr= initialization, and stores the result as a ready-to-inspect =forth_program=.
Every capacity is its own template parameter with a project-standard default (D2); =BuildDepth=/=BuildRDepth=/=Fuel= size and budget the transient build-time state =build_session= constructs internally.
A =Source= that fails to interpret — an unknown word, a stack underflow, a budget-exhausted top-level loop, or anything else =interpreter::interpret= diagnoses — is a hard compile error: =.value()= on a failed =foundation::result= inside a =constexpr= initializer is not a core constant expression, so the whole translation unit fails to compile (=test_neg_syntax_error.cpp= exercises the failure side deliberately).
This is a strictly *wider* net than R1's own contract caught: since building a session now *is* running the top level, what used to be a separate, later, per-call *runtime* failure (budget exhaustion, for instance) is folded into this same single build-time evaluation too — see DIV-0014 for the consequence this has for a program like the old =SPIN= budget-exhaustion example, whose source text and expected behavior are preserved in =interpreter/control_flow_corpus.hpp= rather than reachable through this API (it also needs control flow, which does not exist until step F27 regardless).

F15's own merge criterion, verbatim, still holds after the retarget: =compiled_forth<": SQUARED DUP * ;  4 SQUARED">.stack()= static-asserts to =[16]= — a one-element stack snapshot whose only cell is =16= (=forth.test.cpp='s =SquaredMergeCriterion=).
The =hello= example (=src/examples/hello.cpp=) runs a small program through =compiled_forth= and prints its =.output()=; =src/examples/godbolt_forth.cpp= is the Godbolt single-file extraction example modeled on =~/src/compile-time-scheme/main/src/examples/godbolt_arithmetic.cpp='s own shape.

* Phase 7: The Text Interpreter, Interpret State Only (step F24, docs/forth-plan-2.md)

Everything above this section describes the R1 pipeline (source text → structural parse → syntax tree → elaboration → codegen → a choice of backend), superseded as the project's front end by DIV-0011's true-Forth pivot (=docs/divergences/DIV-0011-true-forth-pivot.md=).
That pipeline, its tree, and its elaborator are untouched by step F24 and remain fully buildable and tested — the cut that removes them is step F26 — but they are no longer where new front-end work lands.
D13 makes the Forth-2012 section 3.4 outer text interpreter the architecture: parse a word, find it, execute it (interpret state only, as of this step — compiling arrives at F25), else try it as a number per =BASE=, else a positioned diagnosed error; =STATE=, =SOURCE=, =>IN=, and =BASE= are ordinary machine state, not hidden inside any parser.

At the time F24 landed, "machine state grows =SOURCE=/=>IN=/=BASE=/=STATE=" meant a new, composed =smd::forth::interpreter::forth_state=: it wrapped a =machine::forth_state= (the stacks, data space, and output buffer, all unchanged since F8/F10) by composition rather than by editing that type in place, and added an =input_source= plus =BASE= (default 10) and =STATE= (0 = interpreting; F25 is the first step that ever writes a nonzero value).
Composition, not an in-place edit, is what kept every existing consumer of the narrower =machine::forth_state= — =machine::run=, =machine::eval_program=, =forth.hpp='s own =forth_program= — working unchanged while the R1 pipeline those consumers belonged to was still alive.
Step F28 folds this wrapper away (DIV-0012's own deferred half, closed — see Phase 9's own subsection below and Phase 11): =input_source=, =BASE=, and =STATE= are now fields directly on =machine::forth_state= itself (=machine/forth_state.hpp=, relocated from =interpreter/input_source.hpp= to =machine/input_source.hpp= in the same step, re-namespaced =smd::forth::machine=), and =interpreter::forth_state= no longer exists.
This section keeps its own historical framing (composition was the correct, narrower move for F24's own scope, with the R1 pipeline still standing) but every code sample below reflects where those fields live today.

#+transclude: [[file:../src/smd/forth/machine/input_source.hpp::6a8b2e4f-1c9d-4a3e-8f5b-2d7c9e1a4b6f]] :lines 2- :src cpp :end "6a8b2e4f-1c9d-4a3e-8f5b-2d7c9e1a4b6f end"

=>IN= is stored as a bare byte offset, not as a =parser::cursor=, per D19's own instruction that it be ordinary, inspectable machine state rather than a cursor buried inside a scanner's local variables — the property F29's user-defined parsing words will depend on, since a Forth-level word like =PARSE= has to be able to read and write =>IN= through the same interface the outer loop itself uses.
=input_source::cursor_at_in= is the bridge back to the combinator library: it rebuilds a =parser::cursor= by replaying =parser::cursor::bump= from the start of the source text, which is what keeps line/column diagnostics correct without =input_source= maintaining a second, parallel line/column tracker of its own.

The outer loop itself is =interpret=: scan one word via =parser::scan_word= (the D19 token layer discussed in Phase 1, relocated to =parser/= at step F26), look it up in the =machine::dictionary= newest-first (free redefinition shadowing, unchanged since F9), run it through =machine::apply_primitive= if it resolves to a primitive, else classify it as a number per the state's own =BASE= and push it, else diagnose an unknown word at the word's own start position.
Number classification per =BASE= is new machinery, not a generalization of =parser::is_number_token=/=token_to_cell= in place: those two stay fixed to decimal (D8's original scope, predating =BASE=), and =is_number_token_in_base=/=token_to_cell_in_base= sit in =interp.hpp= instead, agreeing with the decimal-only pair at =base == 10= (checked directly, by =static_assert=) and generalizing to any base 2..36 by treating =A=..=Z= as digits 10..35 — which composes for free with D8's case folding, since every token reaching this classification has already been folded to uppercase by =scan_word=.

#+transclude: [[file:../src/smd/forth/interpreter/interp.hpp::aa1d6f83-9b3c-4e2a-8d5f-3c7b1e9a4f62]] :lines 2- :src cpp :end "aa1d6f83-9b3c-4e2a-8d5f-3c7b1e9a4f62 end"

Fuel is architecture now (D22), not only a VM/evaluator concern: =consume_interp_fuel= bounds the outer loop itself, once per token actually processed, the same shape as =machine::consume_vm_fuel= and =machine::consume_fuel= but scoped to a layer neither of those reaches — a source that is nothing but an unbroken stream of valid tokens, none of which ever exhausts a stack or any other already-fueled subsystem, still cannot run the constant evaluator past its own budget undiagnosed.
Every stack/data-space misuse a primitive's own =apply_primitive= diagnoses (underflow, overflow, division by zero, an out-of-bounds =@=/=!=) surfaces through =interpret= completely unchanged — the identical =foundation::parse_error= value, not a re-diagnosed or repositioned one, since D7's machine substrate carries no source-position concept of its own to add.
An unknown word's diagnosis, by contrast, is always positioned: at the scanned token's own start, after any leading whitespace/comment has already been skipped, which is what makes =\= and =( ... )= comments simply vanish as intertoken space rather than ever becoming tokens themselves.

F24's own merge criterion, verbatim: =1 2 + .= run through =interpret= leaves output ="3 "= and an empty data stack; =BASE= defaults to 10 and setting it to 16 makes =FF .= print =255 = (=interp.test.cpp='s =HexBaseHandling=); an unknown word's diagnosed error carries the position of the word itself, not the source's start (=UnknownWordCarriesPosition=); a stack underflow reached through =interpret= is ===-equal, error value for error value, to calling =machine::apply_primitive= directly for the same misuse (=UnderflowMatchesApplyPrimitiveDirectly=).
The F5 number/word tests — =-1= is a number, =1-= is a word — move here intact, now exercised through the full interpreter loop rather than only the token-layer classifier (=NegativeOneIsANumberOneMinusIsAWord=).

* Phase 8: The Colon Compiler and the Session Image (step F25, docs/forth-plan-2.md; extended at step F26)

Step F25 is what first writes =STATE= to a nonzero value: =interpret= (=interp.hpp=) now compiles as well as interprets, and D15's session image gets a first, real type.
At F25 nothing from Phase 7 was deleted yet — the R1 pipeline and F24's own interpret-state-only behavior both still built and passed alongside it; step F26 ("the cut") is what actually removed them, and this section now describes the post-cut state directly rather than narrating the transition.

=machine::emit= (F14's =codegen.hpp=, now history — =docs/history/architecture-grammar-era.org=) relocated to its own header, =machine/emit.hpp=, byte for byte at step F25 — D16's "the emission utilities ... survive as the compiling words' toolkit" instruction, read literally.

=machine::dictionary= gained a sixth binding alternative at step F25, =compiled_colon_word= (=dictionary.hpp=): an entry point into the interpreter's own code space, plus the captured (unverified until F30, D20) declared-effect span.
That was deliberately *not* a reuse of the R1 elaborator's own =colon_word= binding, whose =core_id= was an index into the elaborator's arena; see DIV-0013 for the original reasoning.
Step F26 deletes the elaborator, and =colon_word= (plus its =stack_effect= payload type and =dictionary::define_colon=) along with it: =compiled_colon_word= is now the *only* colon-definition binding kind in =dictionary_binding=, five alternatives instead of six.
DIV-0013 left the rename-or-fold choice at that point to this step's own discretion; F26 keeps the =compiled_= prefix rather than renaming (not worth touching every consumer of the name for a cosmetic gain) — see DIV-0013's own closure note and DIV-0014.

=interpreter::compile_buffer= (=interpreter/compilebuf.hpp=) is the incrementally-appendable code space D15 calls for: a thin wrapper around =machine::compiled_program= (retained per D16, not a second code representation) that grows one instruction at a time via =machine::emit=, as `:` ... `;` pairs are met.
Instruction 0 is reserved at construction as a permanent =halt= landing pad.

#+transclude: [[file:../src/smd/forth/interpreter/compilebuf.hpp::f7a3c9e1-6d4b-4a2f-8c1e-9b5d7a3f2e6c]] :lines 2- :src cpp :end "f7a3c9e1-6d4b-4a2f-8c1e-9b5d7a3f2e6c end"

=call_word= is D14's own "interpreting a defined word runs its code on the VM against the live forth_state" made concrete: it pushes the halt pad's own index as a return address, then calls =machine::run_from= (=vm.hpp=, Phase 9 covers this header's own retained shape in full) at the word's own entry point, against the already-live state.
=run_from= is the genuine additive VM entry point D14/DIV-0013 call for: it runs =run='s own fetch-execute loop starting from an arbitrary instruction index, without =run='s own F16 data-space seeding step — the seeding is a batch, whole-program concern, correct once per top-level run and wrong to repeat on every single interpreted word call (each repeat would =allot= more cells, unconditionally, without bound).
=run= itself is implemented in terms of =run_from= (seed, then delegate to =run_from(program, state, program.program_entry, fuel)=); DIV-0013 records why an earlier draft that instead pointed =compile_buffer='s own =compiled_program::program_entry= at the word being called and reused =machine::run= unmodified was rejected on review (mutating shared, conceptually-const program state to fake an entry point, correct only by an incidental invariant rather than by construction).

=interpret= itself branches on =st.state()=: interpreting (0) runs a primitive, calls a =compiled_colon_word=, or pushes a =variable_word=/=constant_word='s address/value (both against the same live =st=, D14 — there is no second evaluator); compiling (1, entered by `:`) emits =op::prim=/=op::call=/=op::push= into the =compile_buffer= instead of running/pushing.
`:`, `;`, `EXIT`, `RECURSE` (step F25), and `VARIABLE`/`CREATE`/`CONSTANT` (step F26) are all recognized by direct name comparison before any dictionary lookup; step F27 (Phase 10) generalizes this into real immediate-word dispatch through the dictionary for every control word, `IMMEDIATE`, `POSTPONE`, `LITERAL`, `[`, `]`, and `COMPILE,`, without touching this handful of direct-name special cases (they stay exactly as described here). Step F28 (Phase 11) later moves `CREATE` specifically off this list, onto that same generalized dictionary dispatch — required so `CREATE` can also run from *inside* another word's own compiled body — while leaving `VARIABLE`/`CONSTANT` on it, since nothing needs either to work that way yet.
`:` records the entry point (=compile_buffer::here()=) *before* compiling the body, so `RECURSE` (a self-`call` to that same entry point) resolves without any back-patching — F14's discipline, carried forward unchanged.
A declared `( ... -- ... )` effect comment immediately after the name is captured as a =foundation::source_span= (=scan_colon_header=, D20: stored, unverified until F30) rather than silently vanishing as ordinary intertoken space the way any other comment does — capturing it needs its own name scan that skips =parser::scan_word='s usual trailing comment-swallow, since the comment must still be visible afterward to capture.
=VARIABLE=/=CREATE= (step F26; =CREATE= relocated at step F28, Phase 11) allot one cell or zero, respectively, from the data space directly (no elaboration-time data space to coordinate with any more — Phase 4's old =elaborate_variable=/=elaborate_create= are history) and install a =machine::variable_word=; =CONSTANT= pops the data stack's own top cell — ordinary Forth-2012 semantics, not R1's own elaboration-time constant-folding, which required a syntactically preceding literal token.

* Phase 10: Immediacy and Control Flow (step F27, docs/forth-plan-2.md)

D17 makes every control word an *immediate* word on the standard orig/dest discipline, rather than another handful of direct-name special cases alongside `:`/`;`/`EXIT`/`RECURSE` (Phase 8): `IF ELSE THEN`, `BEGIN UNTIL`, `BEGIN WHILE REPEAT`, `DO LOOP +LOOP LEAVE UNLOOP I J`, `LITERAL`, `POSTPONE`, `IMMEDIATE`, `[`, `]`, and `COMPILE,` are all real =machine::dictionary= entries now, found by the same =dict.lookup= every other word goes through, distinguished only by a new binding kind (=control_word=, carrying a =control_builtin= tag) and a new per-entry =immediate= flag (D18's own header-unification direction, narrowly: just the one flag this step needs, not the full classical header F28 owns).

#+transclude: [[file:../src/smd/forth/machine/dictionary.hpp::0d3b390a-1051-4f76-867c-b4f161264827]] :lines 2- :src cpp :end "0d3b390a-1051-4f76-867c-b4f161264827 end"

A =control_word= carries no VM entry point, unlike a primitive (inlined as =op::prim= at every reference site) or a =compiled_colon_word= (real instructions in the code space): its whole job is to mutate the interpreter's own =compile_buffer= directly while a definition is being compiled, which needs C++ code with direct access to that buffer, not anything a VM instruction stream can represent.
That is also why =control_builtin=/=control_word= live in =machine/dictionary.hpp= as a plain data tag rather than as a function pointer: the dispatch logic itself (=interpreter::apply_control_word=) lives one layer up, in =interp.hpp=, which already depends on =machine/=.

D13's own rule — "execute a word when interpreting, or when immediate; otherwise compile it" — is now genuinely uniform across every binding kind, not special-cased per kind the way Phase 8 left it.
=interpreter::execute_entry= is "run this entry's execution semantics against the live state" (a primitive via =apply_primitive=, a colon word via =call_word=, a variable/constant by pushing its address/value, a control word via =apply_control_word=); =interpreter::compile_entry= is "append this entry's own compiled form" (the same four non-control-word cases, minus running); =interpret='s own loop calls =execute_entry= unconditionally while interpreting, and while compiling calls =execute_entry= for an immediate entry or =compile_entry= for an ordinary one.
=POSTPONE=/=COMPILE,= reuse =compile_entry= directly for any target that has a compiled form, which is what gives =POSTPONE= its correct "dual behavior": appending a call/push is the same action whether or not the target happens to be immediate, since immediacy only ever changes what happens when a name is met *without* =POSTPONE=.

#+transclude: [[file:../src/smd/forth/interpreter/interp.hpp::b4e7b8e3-3275-47e2-81da-1c7eb25ae1db]] :lines 2- :src cpp :end "b4e7b8e3-3275-47e2-81da-1c7eb25ae1db end"

=apply_control_word= is where the orig/dest discipline itself lives, D17's "the data stack serving as the control-flow stack as the standard permits" read literally: `IF`/`WHILE` emit a sentinel =op::branch0= (operand =-1=, never a real instruction index) and push the emitted instruction's own index onto the *live* data stack; `THEN`/`ELSE`/`REPEAT` pop that same stack and patch the sentinel to the current code-space position; `BEGIN` pushes a backward-branch target with no instruction of its own.
`DO`/`LOOP`/`+LOOP` carry the F17 counted-loop opcodes verbatim (=do_setup=/=loop_step=/=plus_loop_step=, Phase 9's own instruction-set transclusions, unchanged) and replay F17's own =LEAVE= sentinel-scan token-by-token instead of tree-structured: `DO` pushes its own dest; `LOOP`/`+LOOP` pop it, emit the step instruction, and scan every =op::leave= between dest and the new code-space position still carrying its own =-1= sentinel, patching each to land just past the loop — bounded to exactly this `DO`'s own body, since an inner nested loop's own `LOOP`/`+LOOP` already resolved its own =LEAVE=s first.
`LEAVE`/`UNLOOP`/`I`/`J` outside a `DO ... LOOP` are diagnosed via a private =loop_depth= counter (=interpreter::compiling_context=, transcluded above) rather than by inspecting the control-flow stack's own untyped contents.

**`POSTPONE` of a C++-native control word: a deliberate scope cut.**
`: ENDIF POSTPONE THEN ; IMMEDIATE` is this step's own stated example, and it works — but not by compiling anything: since a =control_word= has no VM entry point, "append code that runs `THEN`'s own action later" is not representable as VM bytecode at all.
=apply_control_word='s own =postpone_= case instead records the target on =compiling_context= (=has_postponed_alias=/=postponed_target=), and =interpret='s own `;` handling, seeing that flag, installs the word being closed as a plain =control_word= alias for the same tag — =ENDIF= becomes, for every purpose, indistinguishable from =THEN= itself — rather than as a =compiled_colon_word=.
This only works when the *entire* body of the definition is that one =POSTPONE=; anything else compiled before or after it is diagnosed rather than silently dropped.
Full Forth-2012 =POSTPONE= permits postponing a control word freely mixed with arbitrary other code in the same definition; that would need a unified code/data representation this project does not have before F28's own header unification, so it is out of scope here and diagnosed, not silently miscompiled.

**An unsound check, tried and reverted.**
An early draft of this step also tried to diagnose an unresolved `IF`/`BEGIN` at `;` by checking that the data stack returned to the depth it had at `:`.
That check is unsound: an immediate word's own body can legitimately leave real data behind when it runs at compile time (`: DOUBLE-IT 21 ; IMMEDIATE` used inside another definition being compiled genuinely leaves a =21= on the stack right then, exactly as `[ ... ] LITERAL`'s own bracketed computation does), which a plain depth comparison cannot tell apart from a genuinely unresolved `IF`.
The final design keeps only the =loop_depth= check for an unresolved `DO` (private bookkeeping, not the shared data stack, so it cannot collide with genuine data); a `THEN`/`REPEAT` with no matching `IF`/`BEGIN` is still diagnosed, just later, when the data stack does not hold what they expect to pop — the "mismatched THEN without IF" merge criterion this step names explicitly.

`LITERAL` pops the top of the data stack and emits it as an =op::push= literal into the definition being compiled; `[`/`]` set `STATE` to 0/1 directly, which is what lets an interpreted computation run between them and leave a value for `LITERAL` to pick up; `IMMEDIATE` flags the dictionary's own most recently defined entry via =machine::dictionary::mark_last_immediate=, regardless of binding kind; `COMPILE,` pops a dictionary index (the =op::push_xt= convention =instruction.hpp= already documented, ahead of F28's own fuller execution-token story) and appends that entry's compiled form via =compile_entry=.

**Merge criteria.**
The complete F13/F16/F17 program battery (=interpreter/control_flow_corpus.hpp=, preserved verbatim by F26 for exactly this) passes through =interpret= unchanged, both at compile time (=static_assert=) and at runtime (Catch2): =ABS= ([7]), =COUNTDOWN= (output ="3 2 1 "=), =SPIN= (budget exhaustion diagnosed under a small VM fuel, not a hang), =UPTO3= ([3]), the =EXIT=-boundary program ([-3 99]), =SUMTO= ([15]), =FIND5= ([5]), =TENS= ([9]), =SUMEVEN= ([20]), and =FIRST= ([3]), plus the two memory-word programs (unaffected, still passing).

=: ENDIF POSTPONE THEN ; IMMEDIATE= followed by =: ABS2 DUP 0< IF NEGATE ENDIF ;  -7 ABS2= leaves =[7]=, proving the alias genuinely behaves like `THEN` (=interp.test.cpp='s =PostponeAliasesAControlWord=); a mismatched `THEN` with no matching `IF` is diagnosed (=MismatchedThenWithoutIfIsDiagnosed=).

** The primitive-XT encoding decision (D18)

D18 leaves the actual encoding open between two options: "a one-instruction stub in code space, or a tagged XT naming the primitive."
This step picks the first: an execution token is a plain code-space instruction index that @ref op::execute jumps to exactly like @ref op::call would (push a return address, then jump) — no dictionary lookup at the VM level at all, ever.
A =compiled_colon_word='s own entry point already qualifies (it is `ret`-terminated by construction, F14's discipline); every other resolvable kind (a primitive, a =variable_word=, a =constant_word=, a =value_word=) has no standing code-space location of its own, so =interpreter::resolve_execution_token= builds one — guarded by a leading unconditional branch that jumps past it, patched to land just after.

#+transclude: [[file:../src/smd/forth/interpreter/interp.hpp::1c9e6a4f-7b3d-4e8a-9c2f-6a1d8b4e3f7c]] :lines 2- :src cpp :end "1c9e6a4f-7b3d-4e8a-9c2f-6a1d8b4e3f7c end"

The guard exists because =resolve_execution_token= can be called with the code space positioned *inside* a still-open colon definition's own body — `'`/`[']` used inside a `[ ... ]` bracket while compiling something else, D13's own bracket-interpreting state — where appending a stub's instructions inline, unguarded, would be silently executed as part of the enclosing definition's own body the next time it runs (its own `ret` would return early, corrupting control flow).
This is the same hazard =apply_control_word='s own `IF`/`WHILE` sentinel-and-patch discipline (Phase 10) already exists to avoid, generalized to a second kind of code-space mutation.
`'` (interpreting only, per Forth-2012) calls this directly and pushes the result; `[']` (compile-only, immediate) calls it and compiles a literal push of the result (=op::push_xt=) into the definition being built instead.
A =control_word=, =foreign_word=, or =defer_word= target has no execution token this function can produce (a control word's whole point is that it has no VM-representable form at all; a not-yet-`IS`sed deferred word's target does not exist yet either) — diagnosed, a documented narrower scope than full Forth-2012 (DIV-0016).

** `CREATE`/`DOES>`: reaching the dictionary from inside a compiled body

The classic test, `: CONSTANT2 CREATE , DOES> @ ;  42 CONSTANT2 LIFE  LIFE`, needs `CREATE` to scan a *new* name and install a *new* dictionary entry each time =CONSTANT2= runs — not once, at =CONSTANT2='s own definition time.
Since a colon word's body, once compiled, runs as pure VM bytecode (=machine::run_from=, no interpreter-level re-entry), `CREATE`/`DOES>` need the dictionary reachable from *inside* that bytecode loop — the one deliberate exception to "the VM only ever sees a forth_state" this project has, and the reason =run_from=/=run=/=call_word= all gain a new, nullable, non-owning dictionary pointer parameter (default `nullptr`, exactly what every caller before this step already implicitly assumed).

** `VALUE`/`TO` and `DEFER`/`IS`: two more data-space-backed bindings

=value_word= and =defer_word= (`machine/dictionary.hpp`) both hold a single data-space address rather than growing the dictionary entry itself, deliberately: it lets a compiled *reference* to either (from inside another word) reuse ordinary, already-existing opcodes (`push address`; `prim fetch`; and, for a deferred word, `execute`) rather than needing a new VM/dictionary channel the way `CREATE`/`DOES>` do.

`VALUE`/`DEFER` (non-immediate) install their own binding directly when interpreted, exactly like `CREATE`/`VARIABLE`; `TO` is immediate (it must resolve its target's address once, at the moment it is met, regardless of `STATE`) and either stores the popped value directly (interpreting) or compiles the equivalent push-address/store sequence (compiling).
`IS` pops an execution token (produced by `'`) and stores it straight into the target's own data-space cell — no dictionary mutation at all, unlike `DOES>`.
A deferred word invoked before `IS` is diagnosed with a specific message when found directly by name (=execute_entry='s own =defer_word= case checks the `-1` sentinel); a *compiled* reference to the same word (from inside another definition) instead lets the sentinel reach =op::execute= and diagnoses as an out-of-range instruction pointer — a documented, minor asymmetry, not a gap (D7: both are diagnosed, never UB, just with different specificity).

It does *not*, and cannot, for the structural, orig/dest-patching control words (`IF`/`THEN`/`DO`/`LOOP`/...): their entire action *is* mutating the compile buffer directly, which is not a runtime effect any XT encoding could ever name — giving `THEN` a header/XT slot would not create an action for `EXECUTE` to invoke, because `THEN` has none.
This is a structural fact about what these words are, not a scope cut this step failed to close; DIV-0015's own record is updated in place with this resolution.

* Phase 12: Parsing Words and Strings (step F29, docs/forth-plan-2.md)

** `PARSE`/`WORD`/`CHAR`/`COUNT`/`TYPE` are ordinary primitives, not control words

Every one of these five only needs `state.source()` and `state.data_space()`, both plain fields of `machine::forth_state` since step F28's own fold (Phase 11), so each is a real `machine::primitive` enumerator, dispatched through `apply_primitive` exactly like `DUP`/`@`/`ALLOT` — no dictionary access, no new opcode.
This is the concrete reason `PARSE`/`WORD` used *inside* a colon definition read text from wherever `SOURCE`/`>IN` happen to be *when that definition later runs*, not text present at its own definition: being ordinary, non-immediate words, a compiling dispatch on them emits `op::prim` (D13's own rule, unchanged), so their own scanning action fires at the compiled word's own call time, exactly like any other primitive's side effect.

`scan_delimited` is the one shared scan every parsing word in this project is built from — `PARSE` (no leading skip), `WORD` (skip leading delimiters first, and store a *counted* string per D21 rather than a bare address/length pair), and the reexpressed `(`/`S"`/`."`/`ABORT"` below, differing only in the delimiter, the leading-skip flag, and what each does with the result.
`CHAR`/`[CHAR]` use a second, narrower combinator, `scan_bare_name` (same file): a raw, unfolded, capacity-unlimited blank-delimited name scan, since only the first character of the result is ever consulted.
`PARSE`/`WORD` copy their result into freshly allotted data-space cells (D21: one cell per character) rather than a reusable scratch buffer — a deliberate choice, not an oversight: every other allotting word already in this project (`CREATE`, `VALUE`, `DEFER`, `,`) grows data space monotonically too, so a loop that calls `WORD` many times consumes data space the same way a loop calling `CREATE` many times would, bounded by the caller's own `MaxData`, not by a hidden separate capacity.

** `(`/`\`: reexpressed from scanner-level skipping into ordinary immediate words

Through step F28, `\`/`(` comments were swallowed by the scanner itself (`skip_forth_space`, `parser/forth_chars.hpp`) before a token was even identified.
This step deletes that function (along with `forth_lexeme`): `scan_word`'s own trailing skip is now plain whitespace only (`lexeme`, already existing), so a source `(` or `\` character survives as an ordinary one-character token whenever the next character is whitespace — the same self-delimiting convention every other Forth-2012 word relies on.
Two new, immediate, non-compile-only `control_builtin` tags (`paren_`, `backslash_`) give them real dictionary entries: found and dispatched by `interpret()`'s own token loop exactly like any other word, each scans forward from `state.source()` for its own terminator (`)` or end of line) via `scan_delimited` and advances `>IN` past it.
An unterminated `(` is still diagnosed (`scan_delimited`'s own `found_delim` flag reports it); an unterminated `\` (a trailing comment with no newline before end of input) is not an error, matching Forth-2012's own "discard the remainder of the parse area."
One consequence worth naming: a comment can no longer appear *between* `:` and its own name (`: ( oops ) NAME` now names the word `(`, exactly as a raw name-parse would in any Forth-2012 system) — `scan_colon_header` (Phase 8) is unaffected otherwise, and can now use `scan_word`'s own rest cursor directly to find the name's own end, since that trailing skip no longer risks silently consuming a `( ... )` stack-effect comment immediately following it.

** `S"`/`."`/`ABORT"`: parsing their own string at the moment they are met

All three are immediate control words (`apply_control_word`, interp.hpp): each must consume its own following `"`-delimited text right when it is encountered, regardless of `STATE`, the same reason `(`/`\` must.
`S"` stores the string into freshly allotted data space (D21, one cell per character, exactly `WORD`'s own convention) and leaves its address and length — Forth-2012's own `( -- c-addr u )` runtime shape, works identically interpreting (push immediately) or compiling (compile the address and length as two literal pushes, since the data-space address is already fixed by the time compilation runs).
`."` is `S"` plus `TYPE`: interpreting prints the string immediately with no data-space storage at all (nothing has to survive past that one call); compiling stores it (it must survive until the enclosing definition's own later runtime call) and compiles a push-address/push-length/`TYPE` sequence instead of `S"`'s own bare pushes.

`ABORT"` is compile-only (Forth-2012: its interpretation semantics are undefined); at this step (F29), per DIV-0017, it was not yet the real `THROW -2` Forth-2012 calls for — `THROW`/`CATCH` did not exist until F31.

`[CHAR]` scans the next blank-delimited name at the moment it is met (`scan_bare_name`, same as `CHAR`'s own primitive) and compiles a literal push of its first character's own code, rather than leaving that scan for runtime the way the ordinary, non-immediate `CHAR` primitive does.

* Phase 13: CATCH and THROW (step F31, docs/forth-plan-2.md)

Part 11 (F17) recorded, but never checked, that loop-frame teardown assumes the top of the return stack is the loop's own frame.
This step is where that gap gets paid: `THROW` must unwind an arbitrary mix of call frames (a return address), `DO`-loop frames (two cells, above the caller's own return address), whatever a user's `>R` pushed, and `CATCH`'s own handler frames, all sharing one return stack, without ever mis-identifying one for another.

** A handler is found by depth, never by scanning

`machine::forth_state` gains a scalar register, `handler_depth()`/`set_handler_depth(int)` — not a stack slot, alongside `BASE`/`STATE` — naming the return-stack depth *at which* the innermost active `CATCH` handler's own 3-cell frame begins, or `-1` if none is active.
`op::catch_mark` (`xt CATCH`) pops the execution token, pushes that 3-cell frame — the handler-depth register's own previous value, the data-stack depth at the moment of the call, and the instruction index execution resumes at afterward — points the register at this frame's own base, pushes its own return address (the `catch_ok` primitive that follows it, the same "push return address, jump" convention `op::call`/`op::execute` already use), and jumps to the token.

#+transclude: [[file:../src/smd/forth/machine/vm.hpp::5e8b3a1c-6d2f-4c9e-8b7a-3f1d9c6e2a4b]] :lines 2- :src cpp :end "5e8b3a1c-6d2f-4c9e-8b7a-3f1d9c6e2a4b end"

`perform_throw` is the one place `op::throw_op`, `ABORT"`'s own unconditional routing, and the general machine-fault mapping (both below) all unwind: it reads `handler_depth()` directly, calls the new `cell_stack::truncate(int)` *once* to discard everything above the frame — whatever mix of call/`DO`-loop/`>R` cells the caught execution built, all at once, without inspecting any of it — then pops the frame's own 3 cells, truncates the *data* stack to the recorded depth, pushes the thrown code, restores the handler-depth register, and jumps to the resume instruction.
This is what makes `CATCH`/`THROW` correct regardless of F17's own still-unverified assumption: `THROW`'s own unwind never relies on it, or on any assumption about what is between its own target depth and the current top — by the time it is done, that is simply not there anymore.
A caught execution's own normal completion (no `THROW`) reaches the identical frame a different way: its own final `ret` lands on `catch_ok` (a new `machine::primitive`, not a third opcode — no `ip` manipulation is needed for a normal return), which pops the frame, restores the register, and pushes `0`.

** Interpreting-time CATCH/THROW/ABORT reuse the compiled shape

`CATCH`/`THROW`/`ABORT` are ordinary, non-immediate `machine::control_builtin` tags — none is compile-only, and none needs to run early, exactly like `EXECUTE` (D14).
`interp.hpp`'s own `compile_entry` gives each a compiled form (`op::catch_mark`+`prim catch_ok`; a bare `op::throw_op`; `op::push -1`+`op::throw_op` for `ABORT`, literally `-1 THROW`); `apply_control_word`'s own interpreting-time cases append the identical instructions to the live code space — guarded by a leading unconditional branch exactly like `resolve_execution_token` already does for `'` — and run them once via `machine::run_from`, so a `CATCH`/`THROW` typed directly at the top level behaves identically to one compiled into a colon definition (D14's "one semantics" again).
Interpreting `CATCH`'s own resume ip is `compile_buffer::halt_pad` (instruction 0, always `op::halt`) rather than "one past this call's own appended code," since nothing genuinely follows it there; both the normal-completion path and a matching `THROW` need an explicit trailing `branch halt_pad` to land on it.

** Machine faults, mapped where sensible

`run_from`'s own `op::prim` case, on any primitive failure, checks whether a handler is active before consulting `machine_fault_throw_code` — a message-text match against a small table (`"stack overflow"` → `-3`, `"stack underflow"` → `-4`, `"division by zero"` → `-10`, `"data space address out of bounds"` → `-9`) — so every uncaught diagnosis anywhere in this project keeps its original, more specific message verbatim, unchanged from every test that predates this step.
`ABORT"`'s own runtime primitive (`machine::primitive::abort_quote`) is different: its "condition met" failure always routes through `THROW -2`, whether or not a handler is active, because `ABORT"` *is* `THROW -2` (Forth-2012), not merely a fault this project chooses to make catchable — DIV-0017's own revisit condition closes here.
Fuel exhaustion (D22) is deliberately never mapped: it signals a runaway computation the VM itself gave up bounding, not an ordinary condition a `CATCH` should be able to swallow and keep going past.
