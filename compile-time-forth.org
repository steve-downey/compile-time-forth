* smd::forth

This is a presentation-shaped tour of =smd::forth=, a Forth-2012 text
interpreter written in C++26 that runs identically at compile time and at
ordinary runtime.
Every code sample below is transcluded live from the real source tree by a
UUID anchor -- not hand-copied prose that can drift from what actually
compiles -- the same discipline =docs/compiler_architecture.org= (the full
architecture document this presentation summarizes) uses throughout.
Step F36 (consolidation, =docs/forth-plan-2.md=) is what rewrote this file
onto the real system; see that architecture document for the complete
phase-by-phase account, and =docs/forth-limitations.md= for what this
project deliberately does not implement.

** The public API: a Forth program as a template argument

A whole Forth program is an NTTP.
=compiled_forth<Source>= interprets it once, during translation, and the
result -- a trivially copyable session image -- is a namespace-scope
=constexpr= value.
A program that fails to interpret is a hard compile error, the same way a
program that fails to typecheck is.

** There is no separate compile phase

Forth-2012's own outer text interpreter is the architecture: one loop scans
a word, resolves it against the dictionary the instant it is met, and
either runs it (interpreting) or emits code for it (compiling, inside a
=:= ... =;= definition).
There is no syntax tree and no elaboration pass standing between source
text and the code that runs.

** The session image

Code space, dictionary, and data space together are the session: a
trivially copyable literal that survives the one =constexpr= evaluation
that built it into ordinary runtime code, where the stack-machine VM can
run one of its own defined words again.

#+transclude: [[file:./src/smd/forth/interpreter/session.hpp::c6e9f1b3-8a2d-4c7e-9f1a-3b6d8e2c5a7f]] :lines 2- :src cpp :end "c6e9f1b3-8a2d-4c7e-9f1a-3b6d8e2c5a7f end"

** A stack-effect lint, advisory unless a declared effect commits to one

An abstract interpretation over each definition's own emitted code checks
branch/loop agreement, return-stack balance, and -- when a colon
definition's own =( ... )= comment declares one -- the declared effect
against what the definition actually computes.

#+transclude: [[file:./src/smd/forth/interpreter/effect_lint.hpp::3fd1b4b2-6cf1-4b6e-9b6b-3f2c0a8f7d21]] :lines 2- :src cpp :end "3fd1b4b2-6cf1-4b6e-9b6b-3f2c0a8f7d21 end"

A declared effect that disagrees with the computed one is a diagnosed,
positioned error -- =": BADDECL ( n -- n n ) DUP DROP ;"= fails to compile,
and =test_neg_effect_mismatch.cpp= (step F36) exercises exactly that
failure deliberately.

** A second executor of the same code: the sender/receiver backend

Every compiled instruction stream can also run through an Execution26
sender/receiver graph -- a second, runtime-only executor, not a second code
path fed by anything upstream of the VM.

** Forth metaprogramming is just programming: the bootstrap prelude

Some of this project's own dictionary is written in Forth, not C++.
=NIP=/=TUCK=/=?DUP= are ordinary colon-word compositions; =WHEN=/
=OTHERWISE=/=ENDIF= are each a whole-body =POSTPONE= of =IF=/=ELSE=/=THEN=
-- a full =IF= replacement holds under new names, built entirely with
machinery every earlier step already installed.

** A foreign word is an ordinary word

Calling into C++ from Forth, and Forth from C++, uses the same dispatch
path every other word does -- there is no FFI-aware special case anywhere
downstream of the dictionary.
